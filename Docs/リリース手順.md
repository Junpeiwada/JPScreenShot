### 未登録: `ASC_ISSUER_ID`

公証に必要な最後の 1 件。**Issuer ID はキーごとではなくチーム共通の値**で、API キーの `.p8` ファイルには含まれない（作成画面にしか表示されない）。GitHub Secrets は登録後に値を読み出せないため、JPPhotoTools 側からも複製できない。

1. [App Store Connect → Users and Access → Integrations → App Store Connect API](https://appstoreconnect.apple.com/access/integrations/api) を開く
2. 画面上部の **Issuer ID**（UUID 形式。`69a6de77-…` で始まる）をコピー
3. 登録する:

```sh
printf '<コピーしたUUID>' | gh secret set ASC_ISSUER_ID --repo Junpeiwada/JPScreenShot
```

> `~/Dropbox/アプリ/JPScreenShot/` に `Issuer ID.txt` として置いておくと、次回証明書を触るときに探し直さずに済む。

## 1. 一度だけ行うセットアップ

### 1-1. Sparkle 署名鍵

Sparkle は appcast（更新情報）を EdDSA 署名で検証する。公開鍵をアプリに埋め込み、秘密鍵で CI が署名する。

**JPScreenShot では実施済み。** 秘密鍵はこの Mac のログインキーチェーンに保存され、CI 用に Secret `SPARKLE_PRIVATE_KEY` へ登録してある。

> 鍵は JPPhotoTools と**共用していない**。appcast の署名鍵は配布チャネル単位で分けておくと、片方が漏れたときの影響範囲を切り離せる。

再生成が必要になった場合の手順:

```sh
curl -fL -o sparkle.tar.xz \
  https://github.com/sparkle-project/Sparkle/releases/download/2.9.3/Sparkle-2.9.3.tar.xz
mkdir -p sparkle-tools && tar -xf sparkle.tar.xz -C sparkle-tools

./sparkle-tools/bin/generate_keys          # 生成（公開鍵が表示される）
./sparkle-tools/bin/generate_keys -p       # 既存の公開鍵を確認するだけ
./sparkle-tools/bin/generate_keys -x k.txt # CI 登録用に秘密鍵を書き出す
```

出力された公開鍵を [project.yml](../project.yml) の `SUPublicEDKey` に反映し、`xcodegen generate` で `JPScreenShot-Info.plist` を更新してコミットする。

> ⚠️ 書き出した秘密鍵ファイルは**リポジトリにコミットしない**。Secret 登録後は削除してよい（原本はキーチェーンに残る）。

### 1-2. Developer ID 証明書

Mac App Store 外で配布するには **Developer ID Application** 証明書が必要。**同一チームの既存証明書をそのまま流用できる**（アプリごとに取り直すものではない）。

現状はキーチェーンに以下が入っている:

```
Developer ID Application: Junpei Wada (L897K2C26B)   ← 配布・公証用
Apple Development: Junpei Wada (AV678AWM9H)          ← 開発ビルド用
```

CI へ渡すには `.p12` 形式に書き出して Base64 化する:

```sh
base64 -i DeveloperID.p12 | pbcopy
```

> 実物は `~/Dropbox/アプリ/JPScreenShot/証明書.p12`（パスワードは同ディレクトリの `パスワード.txt`）。

### 1-3. 公証用 App Store Connect API キー

`notarytool` はパスワード方式より API キー方式が安定。**API キーはチーム単位**で、Mac App Store 外配布なら App Store へのアプリ登録は不要。

1. [App Store Connect → Integrations → App Store Connect API](https://appstoreconnect.apple.com/access/integrations/api) でキーを作成（Role: Developer で可）
2. `AuthKey_XXXXXXXXXX.p8` を Base64 化: `base64 -i AuthKey_XXXXXXXXXX.p8 | pbcopy`
3. **Key ID**（ファイル名の `XXXXXXXXXX`）と **Issuer ID**（画面上部の UUID）を控える

> `.p8` は**ダウンロードが一度きり**。紛失したら再作成になる。実物は `~/Dropbox/アプリ/JPScreenShot/AuthKey_5NFM2RND38.p8`（Key ID は同ディレクトリの `キーID.txt`）。

### 1-5. GitHub Pages を有効化する

appcast とランディングページの配信先。**`gh-pages` ブランチは初回リリースのワークフローが自動生成する**ので、この設定は初回リリース後に行う。

1. **Settings → Pages** を開く
2. **Source** を `Deploy from a branch`、**Branch** を `gh-pages`、フォルダ `/ (root)`
3. 公開 URL は `https://junpeiwada.github.io/JPScreenShot/`

この URL が [project.yml](../project.yml) の `SUFeedURL`（`.../appcast.xml`）と一致していること。**一致しないと自動更新が動かない。**

## 2. リリースを発行する（毎回）

セットアップ済みなら、タグ push だけで完結する。

```sh
git tag v0.1.0
git push origin v0.1.0
```

### ショートカット: `Tools/release.sh`

バージョン更新 → コミット → タグ → push を 1 コマンドにまとめたヘルパ。

```sh
Tools/release.sh 0.1.0        # 確認プロンプトあり
Tools/release.sh 0.1.0 -y     # 確認なしで発火
Tools/release.sh --help
```

ワーキングツリーが汚れている／タグが既存の場合は安全のため中断する。

### 発行後の確認

- **Releases** に zip が添付されているか
- `https://junpeiwada.github.io/JPScreenShot/appcast.xml` が最新版を指しているか
- 旧バージョンのアプリで、メニュー「更新を確認…」から更新が検出されるか
- ダウンロードした `.app` の初回起動で Gatekeeper 警告が出ないか（公証・ステープルが効いていれば出ない）

## 3. バージョン番号の運用

- `MARKETING_VERSION`（表示用）は**タグの値が優先**され、CI が上書きする。`project.yml` の値はローカルビルド時の既定値
- タグは必ず `v` プレフィックス付き（`v1.2.0`）
- Sparkle が新旧を判定する `CFBundleVersion` は、単調増加する **GitHub Actions の run 番号**を自動採用する。手動管理は不要

## 4. CI が何をしているか

[.github/workflows/release.yml](../.github/workflows/release.yml) の流れ。

1. `xcodegen generate` でプロジェクトを生成（`.xcodeproj` は Git 管理外なので必須）
2. Sparkle 公開鍵が未設定のままでないかガード
3. Developer ID 証明書を一時キーチェーンへインポート
4. `xcodebuild archive` で Release 構成をアーカイブ（署名は Manual + Developer ID）
5. `-exportArchive` で `.app` を取り出す（`ExportOptions.plist` により Sparkle も再署名）
6. `notarytool submit --wait` で公証 → `stapler staple` で結果を添付
7. 配布 zip を作り **GitHub Release を作成**（リリースノートは自動生成）
8. `generate_appcast` で `appcast.xml` を生成（秘密鍵で署名）
9. `appcast.xml` と `site/` を **gh-pages へ publish**

ランナーは **`macos-26`**。`project.yml` の `deploymentTarget: macOS 26.0` をビルドするには macOS 26 SDK が必要なため、`macos-15` では通らない。

## 5. つまずきやすい点

### Info.plist は生成物だが版管理している

Sparkle の `SUFeedURL` / `SUPublicEDKey` は `INFOPLIST_KEY_*` ビルド設定では注入できないため、実 `Info.plist` を XcodeGen に生成させている。

**真実のソースは [project.yml](../project.yml)。** `JPScreenShot-Info.plist` を直接編集しても次の `xcodegen generate` で消える。設定を変えるときは `project.yml` を編集して再生成し、両方をコミットする。

### 画面収録の権限は署名の同一性に紐づく

開発用（`Apple Development`）と配布用（`Developer ID`）は**別の署名**なので、配布版を初めて起動すると画面収録の許可を改めて求められる。開発中に許可していても引き継がれない。想定内の挙動。

詳細は [実装計画.md 1.3](実装計画.md#13-権限-署名-id-に紐づく開発時の落とし穴) を参照。

### 公証は Apple のサーバ待ちで数分かかる

`notarytool submit --wait` はワークフローを止めて完了を待つ。通常は 1〜5 分。混雑時はさらに伸びる。

### `site/` が無いとワークフローが失敗する

`cp -R site/.` のステップがあるため、ランディングページを消すとリリースが落ちる。不要にする場合はそのステップも削除する。
