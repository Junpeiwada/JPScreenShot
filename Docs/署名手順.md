## 0. なぜこの手順が必要か

理由は 2 つある。どちらも「開発用署名のままでは配布できない」ことに帰着する。

**理由 1: Gatekeeper。** インターネットからダウンロードした `.app` には隔離属性（`com.apple.quarantine`）が付く。Developer ID 署名と公証の両方が揃っていないと、初回起動時に「開発元を検証できないため開けません」と拒否される。開発用の `Apple Development` 証明書は**自分の Mac でしか通用しない**ため、他人の Mac では必ず弾かれる。

**理由 2: 画面収録権限（TCC）。** 本アプリの中核機能は ScreenCaptureKit であり、画面収録権限が必須である。この権限は**署名された識別情報に紐づく**（[実装計画.md](実装計画.md) 1.3）。署名が不正または不安定だと、利用者側で「許可しても起動のたびにリセットされる」という開発中に踏んだのと同じ問題が発生する。配布物では Developer ID による安定した同一性が前提になる。

App Sandbox は無効のため Mac App Store 配布は対象外である（[実装計画.md](実装計画.md) 8.1）。本手順は**直接配布（GitHub Release で zip / dmg を置く）**のみを扱う。

## 2. 前提: Apple Developer Program

Developer ID 証明書の発行には **Apple Developer Program への加入（年額 11,800 円 / $99）が必須**である。無料の Apple ID では発行できない。

加入状態は以下で確認する。

- <https://developer.apple.com/account> を開く
- 「Membership details」に Team ID が表示され、`L897K2C26B` と一致すること
- 有効期限が切れていないこと（**失効すると証明書も使えなくなる**）

未加入の場合は、まず加入手続きを行う（審査に数日かかることがある）。加入せずに配布したい場合は [11 章](#11-つまずきやすい点)の「代替案」を参照。

## 3. Developer ID Application 証明書の作成

配布用アプリの署名には **`Developer ID Application`** 証明書を使う。`Apple Development` でも `Apple Distribution`（App Store 用）でもない点に注意する。

### 手順（Xcode 経由が簡単）

1. Xcode → Settings → Accounts
2. Apple ID を選び、Team `L897K2C26B` を選択
3. 「Manage Certificates...」→ 左下の `+` → **「Developer ID Application」**を選ぶ
4. 生成後、キーチェーンに秘密鍵とセットで保存される

### 手順（Web 経由）

1. <https://developer.apple.com/account/resources/certificates/list>
2. `+` → **Developer ID Application** → Continue
3. CSR（証明書署名要求）をアップロードする
   - キーチェーンアクセス.app → メニュー「キーチェーンアクセス」→ 証明書アシスタント → 「認証局に証明書を要求...」
   - メールアドレスと通称を入力し、「ディスクに保存」＋「鍵ペア情報を指定」を選ぶ
   - 鍵のサイズ 2048 ビット / アルゴリズム RSA
4. 発行された `.cer` をダウンロードしてダブルクリックし、キーチェーンに追加

### 確認

```sh
security find-identity -v -p codesigning
```

`Developer ID Application: Junpei Wada (L897K2C26B)` のような行が出れば成功。**この文字列を [6 章](#6-projectyml-を配布用に整える)でそのまま使う**ので控えておく。

> 注意: Developer ID 証明書は**1 チームあたり最大 5 個**まで。使い回すのが基本で、Mac を移行する場合は新規発行ではなくキーチェーンから `.p12` で書き出して移すこと。秘密鍵を失うとその証明書は二度と使えない。

## 4. App Store Connect API キーの作成（公証用）

公証には Apple への認証が必要である。方式は 2 つあるが、**API キー方式を推奨**する（app-specific password 方式は Apple ID とパスワードの管理が煩雑なため）。

1. <https://appstoreconnect.apple.com/access/integrations/api> を開く
2. 「Team Keys」タブ → `+` で新規キーを作成
3. 名前は任意（例: `JPScreenShot Notary`）、アクセス権は **「Developer」**で足りる
4. 生成された `AuthKey_XXXXXXXXXX.p8` を**ダウンロードする**
   - **ダウンロードは 1 回きり**。紛失したら作り直しになる
   - `~/private_keys/` などに保管し、**絶対に git にコミットしない**
5. 以下 3 つを控える
   - **Key ID**（例: `XXXXXXXXXX`）
   - **Issuer ID**（ページ上部に表示される UUID）
   - `.p8` ファイルのパス

## 5. notarytool の認証情報を保存

毎回 3 つの引数を渡すのは面倒なので、キーチェーンにプロファイルとして保存する。

```sh
xcrun notarytool store-credentials "JPScreenShot-Notary" \
  --key ~/private_keys/AuthKey_XXXXXXXXXX.p8 \
  --key-id XXXXXXXXXX \
  --issuer 00000000-0000-0000-0000-000000000000
```

以降は `--keychain-profile "JPScreenShot-Notary"` だけで公証できる。

確認:

```sh
xcrun notarytool history --keychain-profile "JPScreenShot-Notary"
```

エラーにならず履歴（初回は空）が返れば成功。

## 6. project.yml を配布用に整える

現在の `project.yml` は開発用署名で固定されている。これは**画面収録権限を安定させるための意図的な設定**（[実装計画.md](実装計画.md) 1.3）なので、消さずに **Release 構成でのみ Developer ID に切り替える**。

```yaml
settings:
  base:
    # ... 既存の設定はそのまま ...
    CODE_SIGN_STYLE: Manual
    DEVELOPMENT_TEAM: L897K2C26B
  configs:
    Debug:
      # 開発時は Apple Development で固定（TCC の同一性維持。実装計画 1.3）
      CODE_SIGN_IDENTITY: "Apple Development"
    Release:
      # 配布は Developer ID。公証の前提として Hardened Runtime が必須
      CODE_SIGN_IDENTITY: "Developer ID Application"
      ENABLE_HARDENED_RUNTIME: YES
```

変更後は必ず再生成する。

```sh
xcodegen generate
```

### 補足: Hardened Runtime と ScreenCaptureKit

公証には Hardened Runtime が必須である（既に `ENABLE_HARDENED_RUNTIME: YES` が設定済み）。ScreenCaptureKit と Vision は Hardened Runtime 下でも**追加のエンタイトルメント不要**で動作する。JIT やライブラリ検証の緩和も不要。

App Sandbox は無効のままでよい（直接配布では必須ではない）。

## 7. ビルドと署名

XcodeGen プロジェクトなので、`archive` からエクスポートする。

```sh
cd /Users/junpeiwada/Documents/Project/JPScreenShot
xcodegen generate

xcodebuild archive \
  -project JPScreenShot.xcodeproj \
  -scheme JPScreenShot \
  -configuration Release \
  -archivePath build/JPScreenShot.xcarchive \
  -destination 'generic/platform=macOS'
```

エクスポート用の設定ファイルを用意する（`build/ExportOptions.plist`）。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>method</key>
    <string>developer-id</string>
    <key>teamID</key>
    <string>L897K2C26B</string>
    <key>signingStyle</key>
    <string>manual</string>
</dict>
</plist>
```

エクスポート:

```sh
xcodebuild -exportArchive \
  -archivePath build/JPScreenShot.xcarchive \
  -exportOptionsPlist build/ExportOptions.plist \
  -exportPath build/export
```

`build/export/JPScreenShot.app` ができる。署名を確認する。

```sh
codesign -dv --verbose=4 build/export/JPScreenShot.app
```

以下を満たしていること。

- `Authority=Developer ID Application: Junpei Wada (L897K2C26B)`
- `TeamIdentifier=L897K2C26B`
- `flags=0x10000(runtime)` ← **Hardened Runtime が有効**
- `Signature=adhoc` に**なっていない**こと

## 8. 公証と staple

公証は zip（または dmg）を Apple に送って検査を受ける工程。`.app` を直接は送れないので固めてから送る。

```sh
# 公証用に固める（ditto を使うこと。Finder の圧縮や zip コマンドは署名を壊すことがある）
ditto -c -k --keepParent build/export/JPScreenShot.app build/JPScreenShot.zip

# 公証（完了まで待つ。通常 1〜5 分）
xcrun notarytool submit build/JPScreenShot.zip \
  --keychain-profile "JPScreenShot-Notary" \
  --wait
```

`status: Accepted` が返れば成功。`Invalid` の場合はログを見る。

```sh
xcrun notarytool log <submission-id> --keychain-profile "JPScreenShot-Notary"
```

公証の結果を `.app` 本体に貼り付ける（**staple**）。これをやっておくとオフラインでも Gatekeeper が検証できる。

```sh
xcrun stapler staple build/export/JPScreenShot.app
```

> 重要: **staple するのは `.app` であって zip ではない。** 公証に送った zip は捨て、staple 済みの `.app` を**もう一度固め直して**配布する。

```sh
# 配布用に固め直す
ditto -c -k --keepParent build/export/JPScreenShot.app build/JPScreenShot-1.0.0.zip
```

## 9. 配布前の検証

配布物が本当に他人の Mac で開けるかを、ローカルで確認する。

```sh
# staple されているか
xcrun stapler validate build/export/JPScreenShot.app

# Gatekeeper の評価（これが最も実態に近い検証）
spctl -a -vvv -t install build/export/JPScreenShot.app
```

`source=Notarized Developer ID` と `accepted` が出れば配布可能。

さらに念を入れるなら、隔離属性を付けて初回起動を再現する。

```sh
# 配布物を展開して隔離属性を付与し、ダウンロード直後を再現する
xattr -w com.apple.quarantine "0083;00000000;Safari;" /path/to/展開したJPScreenShot.app
open /path/to/展開したJPScreenShot.app
```

警告なしに起動し、メニューバーにアイコンが出れば成功。**画面収録権限のダイアログが出て、許可後に再起動しても許可が維持されること**まで確認する（[実装計画.md](実装計画.md) 1.3 の問題が配布物で再発しないことの確認）。

## 10. GitHub Release への添付

リポジトリを public にした上で、タグを打って Release を作る。

```sh
# まだ push していない場合
git push -u origin main

# 公開設定
gh repo edit Junpeiwada/JPScreenShot --visibility public --accept-visibility-change-consequences

# タグと Release
git tag v1.0.0
git push origin v1.0.0

gh release create v1.0.0 \
  build/JPScreenShot-1.0.0.zip \
  --title "JPScreenShot v1.0.0" \
  --notes "初回リリース。範囲キャプチャと OCR によるテキスト抽出に対応。"
```

Release ノートには最低限これを書く。

- **動作環境**: macOS 26 以降
- **初回起動時に画面収録の許可が必要**であること（システム設定 → プライバシーとセキュリティ → 画面収録）
- OCR はオンデバイス処理で、**画像を外部送信しない**こと（要求仕様 7 章）

## 11. つまずきやすい点

### 公証が Invalid になる主因

| 症状 | 原因 | 対処 |
|---|---|---|
| `The signature does not include a secure timestamp` | `codesign` に `--timestamp` が無い | Xcode の archive 経由なら自動で付く。手動署名なら `--timestamp` を付ける |
| `The executable does not have the hardened runtime enabled` | Hardened Runtime 無効 | `ENABLE_HARDENED_RUNTIME: YES` を Release に設定（[6 章](#6-projectyml-を配布用に整える)） |
| `The binary is not signed with a valid Developer ID certificate` | `Apple Development` で署名している | Release 構成の `CODE_SIGN_IDENTITY` を確認 |
| zip 展開後に署名が壊れる | Finder 圧縮や `zip` コマンドを使った | **`ditto -c -k --keepParent` を使う**（[8 章](#8-公証と-staple)） |

### 証明書の有効期限

Developer ID 証明書の有効期限は 5 年だが、**Apple Developer Program の会員資格が切れると証明書も無効になる**。ただし、**失効前に公証済みのアプリは引き続き起動できる**（公証のチケットは会員資格と独立）。更新を忘れても既存の配布物が突然死ぬわけではないが、新規ビルドはできなくなる。

### 代替案: Developer Program に加入しない場合

年額を払わない選択もありうる。その場合は**バイナリを配布せず、ソース配布のみ**とするのが現実的。

```
README に記載する手順:
  brew install xcodegen
  xcodegen generate
  open JPScreenShot.xcodeproj   # Xcode で Run
```

利用者が自分の Apple ID（無料）で署名してビルドすれば、画面収録権限も自分の署名に紐づいて安定する。**未署名 / ad-hoc の `.app` を zip で配るのは避けること** — 利用者側で「許可しても毎回リセットされる」問題（[実装計画.md](実装計画.md) 1.3）が起き、体験として成立しない。

### 秘密情報の扱い

以下は**絶対に git にコミットしない**。`.gitignore` への追加を検討する。

- `AuthKey_*.p8`（App Store Connect API キー）
- `*.p12`（証明書と秘密鍵の書き出し）
- `build/`（既に `.gitignore` 済み）
