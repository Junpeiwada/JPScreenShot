## 1. 事前検証の結果

実装方針に影響する 4 点を、計画確定前に実機で確認した。

### 1.1 Vision: 新 API を採用する（仕様からの変更）

仕様 9 章は `VNRecognizeTextRequest` を指定しているが、**新しい `RecognizeTextRequest`（Swift 専用・構造体・async）を採用することを提案する。**

SDK で確認した事実:

| 項目 | `VNRecognizeTextRequest`（旧） | `RecognizeTextRequest`（新） |
|---|---|---|
| 形態 | `class`（ObjC 由来・可変参照） | `struct`（`Sendable`） |
| 実行 | `VNImageRequestHandler.perform` 同期 | `try await request.perform(on:)` |
| 言語指定 | `[String]` | `[Locale.Language]` |
| Swift 6 厳格並行 | 参照型のため隔離の扱いが煩雑 | **警告ゼロで通る** |

採用理由は Swift 6 の厳格並行モードとの相性である。本アプリは「OCR でメイン UI をブロックしない」（非機能要求・応答性）を満たすため OCR を並行実行するが、旧 API は参照型のため `Sendable` 境界を越える際に追加の隔離設計が必要になる。新 API は値型かつ async なので、`await` するだけで要求を満たせる。

**検証済み**: 下記コードが `-swift-version 6 -strict-concurrency=complete` で**警告ゼロでコンパイル**することを確認した。

```swift
var request = RecognizeTextRequest()
request.recognitionLevel = .accurate
request.recognitionLanguages = [Locale.Language(identifier: "ja-JP"),
                                Locale.Language(identifier: "en-US")]
request.usesLanguageCorrection = true
let observations = try await request.perform(on: cgImage)
```

なお `RecognizeTextRequest.Revision` は `revision3` のみで、これは旧 API の最新リビジョンと同一の認識エンジンである。**したがって仕様 6.1 の実測精度（日本語 99.5〜100%）はそのまま有効**であり、API 変更による精度の再検証は不要。認識レベル `.accurate`・言語指定・言語補正 on/off という 6.3 の設計もすべて新 API で表現できる（上記のとおり全プロパティが存在する）。

> 補足: 旧 API はヘッダ上で明示的に `deprecated` とはされていない（`API_AVAILABLE(macos(10.15))` のまま）。ただし Apple は macOS 15 以降 Swift 向けの新 API を推奨しており、新規実装で旧 API を選ぶ理由はない。

### 1.2 キャプチャ: フィルタ方式が必須（CAP-04 の要）

ScreenCaptureKit には範囲キャプチャの手段が 2 つあるが、**一方は CAP-04（オーバーレイが写り込まない）を満たせない。**

| API | 範囲指定 | 除外指定 | CAP-04 |
|---|---|---|---|
| `captureImage(in:)`（macOS 15.2+） | 引数 `rect` で直接 | **不可**（フィルタ引数がない） | **満たせない** |
| `captureImage(contentFilter:configuration:)`（macOS 14+） | `config.sourceRect` | `SCContentFilter(display:excludingWindows:)` | **満たせる** |

`captureImage(in:)` は範囲を引数で直接渡せて簡潔だが、コンテンツフィルタを受け取らないため**暗転オーバーレイ自身が写り込む**。範囲選択 UI が必ず画面を覆う本アプリでは採用不可である。

したがって以下の組み合わせを採用する（コンパイル検証済み）:

```swift
let myPID = ProcessInfo.processInfo.processIdentifier
let mine = content.windows.filter { $0.owningApplication?.processID == myPID }
let filter = SCContentFilter(display: display, excludingWindows: mine)

let config = SCStreamConfiguration()
config.sourceRect = rectInPoints            // 選択範囲（ポイント単位）
config.width  = Int(rectInPoints.width  * scale)   // scale = backingScaleFactor
config.height = Int(rectInPoints.height * scale)   // → Retina 解像度を維持（CAP-02）
config.captureResolution = .best
config.showsCursor = false
```

`sourceRect` はポイント単位で与え、`width`/`height` にその `backingScaleFactor` 倍を指定することで、ダウンスケールせず Retina 解像度のまま取得できる（CAP-02）。

### 1.3 権限: 署名 ID に紐づく（開発時の落とし穴）

検証中、未署名 CLI バイナリからのキャプチャは TCC エラーで失敗した。

```
Error Domain=com.apple.ScreenCaptureKit.SCStreamErrorDomain Code=-3801
"ユーザがアプリケーション、ウインドウ、ディスプレイ取り込みのTCCを拒否しました"
```

画面収録権限は**署名されたアプリバンドルの識別情報に紐づく**。実装上の帰結は 2 つある。

1. **権限は必ずアプリバンドルとして起動して確認する。** `swift` スクリプトや素のバイナリでは永久に取得できない。
2. **ad-hoc 署名だと署名が変わるたびに権限が失われる。** 開発中に「昨日は動いたのに今日は拒否される」が起きる典型原因。開発用の署名 ID を固定するのが望ましい。

また `CGPreflightScreenCaptureAccess()`（許可ダイアログを出さずに現状を確認）と `CGRequestScreenCaptureAccess()`（要求）が利用可能であることを確認した。受け入れ基準 10（権限が無いとき案内を出し、無反応にしない）は前者で分岐して実装する。

> 補足: ビルド時に `note: Disabling hardened runtime with ad-hoc codesigning.` が出る。ad-hoc 署名では Hardened Runtime が自動で無効化されるため、配布時は正式な署名 ID が必要。

**実際に発生した問題と恒久対策（段階 3）**: 当初 ad-hoc 署名（`Signature=adhoc` / `TeamIdentifier=not set`）でビルドしていたところ、「**許可を追加しても反映されず、再起動すると再び要求される**」状態になった。

原因は 2 つ重なっていた。

1. **ad-hoc 署名では TCC がビルドごとに別アプリと見なす。** 署名されたアプリは `Identifier` + `TeamIdentifier` で同一性が判定されるが、ad-hoc には Team ID が無いため `CDHash` が使われる。`CDHash` はビルドごとに変わるので、許可が毎回リセットされる。
2. **同じバンドル ID のコピーが 2 つ存在していた。** Xcode 既定の DerivedData 配下にも `JPScreenShot.app` が残っており、LaunchServices がそちらを起動していた。片方に許可を与えても、実際に動くのは別のコピーという状態だった。

対策として `project.yml` に開発用の署名 ID を固定した。

```yaml
CODE_SIGN_STYLE: Manual
CODE_SIGN_IDENTITY: "Apple Development"
DEVELOPMENT_TEAM: L897K2C26B
```

これで `TeamIdentifier=L897K2C26B` が入り、**リビルドしても同一性が保たれる**（`CDHash` が変わっても許可が維持される）ことを確認した。あわせて古い DerivedData のコピーを削除し、`tccutil reset ScreenCapture com.soneru.JPScreenShot` で ad-hoc 時代の登録を消した。

> 開発中に「許可したのに撮れない」が再発したら、まず `pgrep -lf JPScreenShot` で**実際に動いているバイナリのパス**を確認する。意図したビルドとは別のコピーが動いていることがある。

### 1.4 XcodeGen: project.yml をビルドまで検証済み

[3. XcodeGen 設定](#3-xcodegen-設定) の `project.yml` は、XcodeGen 2.44.1 で生成 → `xcodebuild` で **BUILD SUCCEEDED** まで確認した。生成された `Info.plist` に意図した値が入ることも検証した。

```
"CFBundleIdentifier" => "com.soneru.JPScreenShot"
"LSMinimumSystemVersion" => "26.0"
"LSUIElement" => true          ← Dock に出さない（非機能要求・常駐）
```

`LSUIElement` は `INFOPLIST_KEY_LSUIElement: YES` で設定でき、**`Info.plist` を手書きで版管理する必要はない**（`GENERATE_INFOPLIST_FILE: YES` で生成される）。

## 3. XcodeGen 設定

以下をそのまま `project.yml` として配置する（[1.4](#14-xcodegen-projectyml-をビルドまで検証済み) で検証済みの内容に、実装に必要な設定を追加したもの）。

```yaml
name: JPScreenShot
options:
  bundleIdPrefix: com.soneru
  deploymentTarget:
    macOS: "26.0"
  createIntermediateGroups: true

settings:
  base:
    SWIFT_VERSION: "6.0"
    SWIFT_STRICT_CONCURRENCY: complete     # 1.1 の新 API 採用が前提
    MARKETING_VERSION: "1.0"
    CURRENT_PROJECT_VERSION: "1"
    ARCHS: "$(ARCHS_STANDARD)"             # Apple Silicon / Intel ユニバーサル
    CODE_SIGN_STYLE: Automatic
    ENABLE_HARDENED_RUNTIME: YES

targets:
  JPScreenShot:
    type: application
    platform: macOS
    sources:
      - path: Sources
    settings:
      base:
        PRODUCT_BUNDLE_IDENTIFIER: com.soneru.JPScreenShot
        GENERATE_INFOPLIST_FILE: YES
        INFOPLIST_KEY_LSUIElement: YES     # Dock に出さない
        COMBINE_HIDPI_IMAGES: YES
        ENABLE_APP_SANDBOX: NO             # 下記注記を参照
```

補足:

- **`.xcodeproj` は生成物なので `.gitignore` に入れる**（仕様 9 章）。`xcodegen generate` で再生成する。
- **Xcode の「Update to recommended settings」は `project.yml` 側で対応する。** Xcode のボタンで直すと生成物である `.xcodeproj` が書き換わり、次の `xcodegen generate` で消える。推奨設定の実体は Xcode 自身のテンプレート（`/Applications/Xcode.app/Contents/Developer/Library/Xcode/Templates/Project Templates/Base/Base_ProjectSettings.xctemplate/TemplateInfo.plist`）にあり、これと生成済みプロジェクトの差分を取れば不足分が特定できる。
  - 段階 6 時点で不足していたのは 5 つ: `SWIFT_APPROACHABLE_CONCURRENCY` / `SWIFT_UPCOMING_FEATURE_MEMBER_IMPORT_VISIBILITY` / `ENABLE_USER_SCRIPT_SANDBOXING` / `LOCALIZATION_PREFERS_STRING_CATALOGS` / `ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS`。いずれも有効化して警告ゼロでビルドできることを確認済み。
  - `LastUpgradeCheck` は `options.xcodeVersion`（例: `"2650"`）で指定できる。
  - ただし **`compatibilityVersion` は XcodeGen 2.44.1 が `"Xcode 14.0"` に固定**しており、`project.yml` からは変更できない（`compatibilityVersion` / `projectVersion` / `objectVersion` はいずれもエラーにならず黙って無視される）。実害は確認されていないが、これが原因で警告が残る場合は XcodeGen 側の対応待ちになる。
- `SWIFT_VERSION` は Swift **言語モード**の 6 を指す（ツールチェーンの 6.3.2 とは別軸）。
- **App Sandbox は第 1 版では無効にする。** サンドボックス下では「デスクトップへの保存」（SAV-01）にユーザー選択やエンタイトルメントが必要になり、仕様の「デスクトップ固定でよい」という単純さと衝突する。App Store 配布に進む段階で、保存先選択（SAV-04）と併せて再検討するのが妥当。
- 外部依存はないため `packages` セクションは不要（仕様 3 章「外部依存: なし」）。

## 4. モジュール設計

### 4.1 全体の流れ

```
メニューバー左クリック
  → ScreenPermission.ensure()      権限が無ければ案内して中断（基準 10）
  → SelectionCoordinator.begin()   全スクリーンにオーバーレイ
       ├ Esc / 微小選択 / クリックのみ → キャンセル（CAP-05・4.2）
       └ 矩形確定
  → オーバーレイを閉じる            ※キャプチャ前に必ず閉じる（6 章参照）
  → ScreenCaptureService.capture()  フィルタ方式・Retina 維持（CAP-02/04）
  → 結果ウィンドウを表示            画像だけ先に出す（4.3・OCR を待たない）
  → TextRecognizer.recognize()      async・完了後にテキスト欄を更新
```

要求「画像プレビューは OCR 完了を待たず先に表示する」（4.3）を満たすため、**結果ウィンドウの表示と OCR の開始を分離**する。ウィンドウは画像が取れた時点で出し、OCR 中はスピナーを表示、`await` の完了で差し替える。

### 4.2 認識モードと再認識

`RecognitionMode` は仕様 6.3 の表をそのまま型にする。

| モード | `recognitionLanguages` | `usesLanguageCorrection` | 後処理 |
|---|---|---|---|
| `.japanese`（既定） | `["ja-JP", "en-US"]` | `true` | なし |
| `.code` | `["en-US"]` | `false` | `CodeNormalizer` |

- モード切替で**即座に再認識**する（6.3）。キャプチャ画像は結果ウィンドウが保持しているので再キャプチャは不要。
- 直前のモードを `UserDefaults` に保存し次回の既定にする（6.3）。
- `CodeNormalizer` は仕様 6.3 の正規化対象（括弧類・記号・波ダッシュ／長音・全角空白）を実装する。**字形の混同（`l`/`1` 等）は補正しない**（6.3 の明示要求）。

**測定結果（段階 5・未検証項目の解決）**: 仕様 6.3 の注記「`["en-US"]` 単独指定で `l`/`1` の混同が実際に改善するかは未検証」を実測し、**大きく改善することを確認した**。

正解 `if (l == 1 && O != 0) { return; }` を Menlo 24pt で描画して測定:

| モード | 認識結果 | 一致率 |
|---|---|---|
| **コード**（`["en-US"]`・補正 off） | `if (l == 1 && 0 != 0) { return; }` | **97.0%** |
| 日本語（`["ja-JP","en-US"]`・補正 on） | `if （1 == 1 88 0 ！= 0） t returni ｝` | 69.7% |

**差は 27.3 ポイント**。コードモードでは以下がすべて正しく認識された。

- `l`（小文字 L）が `1` に化けない（日本語モードでは化けた）
- `&&` が `88` にならない
- `{` `}` `(` `)` `;` が半角のまま出る（全角化しない）

残る誤りは `O`（大文字オー）→ `0` のみで、これは仕様 6.3 の方針どおり**自動補正しない**（文脈がないと判断できず、正しい文字を壊す危険があるため）。

日本語の文章の精度も再確認した。

| ケース | 結果 |
|---|---|
| 日本語 28pt（2 行） | **100%**（完全一致） |
| 小さい文字 11pt（2 行・行間狭め） | **100%**（完全一致） |

仕様 6.1 の実測値（99.5〜100%）を新 API で再現できており、[1.1](#11-vision-新-api-を採用する仕様からの変更) の「認識エンジンは同一で精度は不変」という判断は妥当だった。

### 4.3 結果ウィンドウ

- レイアウトは**上に画像・下にテキストの縦積み**（4.3 の明示要求）。領域比をドラッグで変えられることが望ましいとあるため、SwiftUI の `VSplitView` を用いる。
- 画像は**アスペクト比を保ち、等倍を超えて拡大しない**（4.3）。`.aspectRatio(contentMode: .fit)` に加えて等倍を上限とする制約を入れる。
- テキストは**選択・編集可能**（4.3）。`TextEditor` を使い、コピー時は編集後の内容を用いる（CPY-02）。
- OCR が 0 文字なら「テキストを認識できませんでした」を表示し、**テキストコピーを無効化**（4.3）。
- コピー成功のフィードバックを出す（CPY-03）。コピー後に閉じるかは環境設定、既定は閉じる（CPY-04）。

## 5. 実装順序

各段階の終わりに動作を確認できる順序にする。前段が壊れていないか常に目視できる。

| # | 段階 | 内容 | 完了条件 |
|---|---|---|---|
| 1 | 土台 | `project.yml`・`.gitignore`・空の `@main`・メニューバー常駐 | Dock に出ず、メニューバーにアイコンが出る |
| 2 | 権限 | `ScreenPermission`・案内 UI | 未許可時に案内が出る（**基準 10**） |
| 3 | キャプチャ | オーバーレイ（暗転・レティクル・寸法・Esc）＋ フィルタ方式取得 | 範囲を撮れて、**オーバーレイが写らない**（基準 1/2/9・CAP-04） |
| 4 | 結果表示 | 結果ウィンドウ（画像のみ）・画像コピー・保存 | 基準 5/7 |
| 5 | OCR | `TextRecognizer`・非同期表示・テキストコピー | 基準 3/4/6 |
| 6 | モード | `RecognitionMode`・`CodeNormalizer`・切替で再認識・記憶 | 基準 8 |
| 7 | 仕上げ | 環境設定・About・非機能要求の計測 | 全基準・8 章の目標値 |

段階 3 を早い位置に置くのは、**CAP-04 と マルチディスプレイが最も失敗しやすい**ためである（[6 章](#6-技術的な要注意点)）。ここが通れば残りは素直に積める。

## 6. 技術的な要注意点

実装中に問題になりやすい箇所を、対処と併せて挙げる。

### 6.1 座標系の不一致（最大の注意点）

macOS には座標系が 3 つ混在する。**マルチディスプレイ（CAP-03）で最も壊れやすい箇所。**

| 座標系 | 原点 | 使う場所 |
|---|---|---|
| AppKit (`NSScreen`) | **左下** origin・Y 上向き | オーバーレイ・マウスイベント |
| CoreGraphics (`CGDisplay`) | **左上** origin・Y 下向き | `SCDisplay` の対応付け |
| ピクセル | — | `config.width/height`（`backingScaleFactor` 倍） |

対処: 変換を 1 か所（`ScreenGeometry`）に集約し、各所で場当たりに `-` しない。副画面が主画面の上や左にある配置（負座標）で必ず確認する。

**注意点**: CoreGraphics の原点は「**主画面の左上**」であり、全画面統合矩形の上端ではない。ここを取り違えると副画面で位置がずれる。

**検証済み（段階 3）**: 実機の 2 画面構成（2560×1440 が横並び、副画面 x=2560）で以下を確認した。

| 検証項目 | 結果 |
|---|---|
| 往復変換の一致（負座標を含む） | OK |
| 主画面上端 → CG で y=0 | OK |
| 副画面の選択 → ディスプレイローカル座標（x=300、2860 ではない） | OK |
| 境界をまたぐ選択 → 面積が大きい画面に寄る | OK |
| 全画面外の選択 → nil | OK |

### 6.2 オーバーレイの写り込み（CAP-04）

`excludingWindows` でアプリのウィンドウを除外するが、**それだけに頼らず、キャプチャ前にオーバーレイを閉じて確実にする**。閉じた直後の 1 フレームは画面がまだ暗いことがあるため、閉じてから撮る順序を守る（[4.1](#41-全体の流れ) の順序）。

### 6.3 オーバーレイウィンドウの設定

**実装時に踏んだクラッシュ（段階 3）**: `NSWindow` の指定イニシャライザは **`init(contentRect:styleMask:backing:defer:)` の 1 つだけ**である（`screen:` 付きは convenience。SDK の `NSWindow.h` で `NS_DESIGNATED_INITIALIZER` が付いているのは前者のみ）。

これを `override` せずに独自の `init(screen:)` を定義すると、継承した指定イニシャライザが未実装のまま残り、AppKit が内部的に呼んだ時点で実行時クラッシュする。

```
Fatal error: Use of unimplemented initializer
'init(contentRect:styleMask:backing:defer:)' for class 'OverlayWindow'
```

対処: 指定イニシャライザを `override` して初期化処理をそこに置き、`init(screen:)` は `convenience` にして `self.init(...)` 経由で通す。`screen:` 付きは convenience なので `override` できない（試すと *initializer does not override a designated initializer* でコンパイルエラー）。

- `level` を `.screenSaver` 相当にして最前面に出す。
- `NSWindow` は既定でキーウィンドウになりにくいため、`Esc` を拾うには `canBecomeKey` を上書きするか `NSEvent` のローカルモニタを使う。
- カーソルは `NSCursor.crosshair`。`cursorUpdate` / `resetCursorRects` で確実に適用する。
- 全スクリーン分のウィンドウを作り、**どれか 1 つで確定したら全部閉じる**。

### 6.4 起動の速さ（200ms 以内・非機能要求）

`SCShareableContent` の取得には時間がかかる。クリックしてから取得を始めると 200ms を超えるおそれがある。対処として、**オーバーレイの表示を先に行い、`SCShareableContent` の取得は並行して進める**（ユーザーが範囲をドラッグしている間に完了させる）。

### 6.5 Swift 6 厳格並行

`SCStreamConfiguration` / `SCContentFilter` / `SCShareableContent` は ObjC 由来の参照型で `Sendable` ではない。`@MainActor` に置くか、生成から使用までを同一の隔離域に閉じる。OCR 側は [1.1](#11-vision-新-api-を採用する仕様からの変更) の新 API により値型で扱えるので、境界を越えるのは `CGImage`（`Sendable` として扱える）に限定できる。

**実装時に判明した制約（段階 3）**: 非 `Sendable` 型は **`Task` の結果型にできない**。`Task<Success, Failure>` の `Success` は隔離に関係なく `Sendable` を要求するため、`Task { @MainActor in ... }` と書いても回避できない。

```swift
// NG: SCShareableContent は非 Sendable なのでコンパイルできない
private var preload: Task<SCShareableContent, Error>?

// OK: 結果は MainActor 隔離のプロパティに格納し、Task は Void を返す
private var preloadedContent: SCShareableContent?
private var preloadTask: Task<Void, Never>?
```

[6.4](#64-起動の速さ200ms-以内非機能要求) の先読みはこの形で実装した。`await preloadTask?.value` で完了を待ち、値はプロパティ経由で受け取ることで境界を越えさせない。

### 6.6 保存（SAV-02）

`JPScreenShot_YYYY-MM-DD_HHmmss.png` は秒単位なので、**同一秒に 2 回保存すると衝突する**。既存ファイルがあれば連番を付けて上書きを避ける（SAV-02 の「上書きしない」）。失敗時は必ず提示する（SAV-03・黙って失敗しない）。

### 6.7 メモリ（非機能要求）

キャプチャ画像は結果ウィンドウを閉じたら解放する。ウィンドウを閉じても `NSWindow` が保持され続けて `CGImage` が残る事故が起きやすいので、閉じる際に明示的に参照を切る。

### 8.1 App Sandbox 無効の位置づけ

本アプリは**作者自身が使う個人ツール**という前提で第 1 版を作る。サンドボックス無効の帰結は次のとおり。

- **利点**: デスクトップへの保存（SAV-01）が追加の許可なしにそのまま動く。ユーザー選択ダイアログもエンタイトルメントの調整も不要で、「撮る→保存」が 1 アクションで完結する（仕様 1 章の目的に直結）。
- **制約**: **Mac App Store では配布できない**（App Store はサンドボックス必須）。直接配布や自分用ビルドは問題ない。
- **将来**: App Store 配布に進む場合はサンドボックスを有効化し、保存先選択（SAV-04）と併せて設計し直す。画面収録権限（[1.3](#13-権限-署名-id-に紐づく開発時の落とし穴)）は正式な署名 ID が前提になる。
